# Decision Register Addendum — Screenshot Evidence Review (DEC-013 .. DEC-024)

**Status:** Proposal — pending stakeholder sign-off. Does not itself satisfy the "no development starts until DEC-001..DEC-012 are signed off" gate; it extends the register with items surfaced by evidence review and must go through the same sign-off process before any dependent work starts.

## Preamble

This addendum is derived from a validated review of **86 screenshots of the reference KapMeta desktop POS application**, captured against a single live outlet ("Hotel kapila"), running app version **126.0.1**, on a **LAN client-server topology** (local outlet server + local terminal clients, syncing to a cloud backend). The screenshots covered 13 distinct feature areas: Table/Floor View, Order Entry/Billing, Online Order Live Feed (Swiggy/Zomato), Mark-OOS Modal, Menu Online-Availability Manager, Order History, Billing Screen Configuration, Bill/KOT Print Configuration, Tax Master, Day-End Payment-Type Summary, Item Report, Restaurant/System Configuration, and the global App Shell/nav.

The purpose of this addendum is twofold:

1. **Inform** the existing DEC-001..DEC-012 items with concrete reference-product evidence where they overlap (e.g. any existing tax, order-status, or multi-outlet decision items), so those discussions are grounded in what the reference app actually does rather than assumption.
2. **Propose new decision items, DEC-013 through DEC-024**, for ambiguities that the screenshot review surfaced and that DEC-001..DEC-012 (as far as can be inferred from the repo README's framing of them as foundational/architectural) may not explicitly cover. These are numbered to continue the existing sequence without renumbering or disturbing the original 12.

All 12 items below are drafted with a real recommended option and rationale — these are opinionated starting proposals for the discovery conversation, **not** final decisions. Every item's Status is `Open` until reviewed and signed off by the listed Owner role (or delegate) per the project's Definition of Ready process.

Cons: risks conflating transient UI/session state (table occupancy) with durable order-record state; "Blank" (no order at all) doesn't naturally belong in an order-status enum. | **Option A** — maintain two distinct, explicitly-named enums: `table_session_state` (Blank/Running/Running-KOT/Printed/Paid, transient, tied to table occupancy) and `order_status` (Saved/Printed/Cancelled/Paid, persisted, tied to the order record), with a documented mapping/derivation. | **DEC-018** | Direction of truth for per-outlet settings (billing/print/tax) | Billing Screen Configuration, Print Configuration, and Tax Master all appear as locally-editable screens on the outlet terminal in the reference app; no screenshot shows a cloud/admin-web equivalent settings screen pushing these down, but the existence of a cloud backend and sync architecture (per repo topology) raises the question of where the authoritative copy lives. | (A) Cloud-authoritative: admin-web is the only place these are edited; local terminal screens become read-only mirrors or are removed. Pros: single source of truth, easy multi-outlet rollout of policy, easy audit. Cons: breaks offline-editability the reference app clearly supports today (screens are live-editable locally); requires connectivity for any local config change. (B) Local-authoritative with async push-up to cloud (mirrors what reference app screenshots show): outlet staff edit locally, changes sync up to cloud for reporting/backup, cloud can display but not silently overwrite. Pros: matches observed reference-app behavior, preserves offline operability. Cons: harder to enforce brand-wide policy consistency across outlets; needs a conflict policy if cloud is later allowed to edit too. (C) Both editable, with cloud writes taking precedence and a last-write-wins or explicit conflict/version-stamp reconciliation. Pros: flexible, supports future centralized-chain use cases. | **DEC-019** | Sync interval / offline-tolerance window | No screenshot directly shows a sync-frequency setting; inferred from System Configuration's "Check Machine"/sync-topology screen and the general LAN client-server design that local operation continues independent of cloud reachability, with online-aggregator orders being the one function that visibly requires connectivity. | (A) Define a hard SLA: outlet must sync within N minutes (e.g. 5) or raise a local alert/degraded-mode banner; local dine-in operations continue regardless; aggregator order intake is disabled/queued while offline. Pros: gives ops and support a concrete, testable threshold; clear customer-facing behavior contract. Cons: arbitrary number needs client validation against real network conditions at outlets. (B) No hard SLA — best-effort eventual sync with no time bound, cloud reporting simply shows "last synced at X" and staff are trusted to notice. Pros: simplest to build. Cons: no proactive degradation signal; risk of an outlet running disconnected for days without anyone noticing, causing large reconciliation gaps and stale cloud-side reporting. | **Option A** — define an explicit sync SLA (proposed default: alert if no successful sync in 15 minutes, hard "degraded mode" banner at 60 minutes) confirmed against real outlet network conditions, with aggregator order intake explicitly documented as unavailable while offline (dine-in/local billing unaffected). Rationale: a POS system's dine-in path must be resilient to network flakiness (which the reference app's local-first architecture already supports), but silent unbounded offline drift is an operational risk that needs a visible threshold, not an assumption that staff will notice. | Engineering Lead | Open |
| **DEC-020** | Local terminal standalone operation if local outlet-server is down | System Configuration's "Check Machine" screen implies a client-server sync topology check exists specifically because terminals depend on the local outlet-server; no screenshot shows what a terminal does if the local server itself is unreachable (distinct from cloud unreachability). | (A) Terminal is fully non-functional without the local server reachable — server is a hard dependency for every terminal action (order entry, billing, printing). Pros: simplest consistency model, avoids split-brain data. Cons: any local-server hiccup halts an entire outlet's operations, including print/billing — high operational risk during peak service. (B) Terminal supports a brief standalone/queued mode: can take orders and print locally-cached menu/pricing data while the local server is unreachable, then reconciles/syncs once the server returns; hard-blocks only genuinely server-dependent actions (e.g. bill-number allocation, which needs the authoritative local sequence). Pros: matches robustness expectations for a restaurant POS during a busy shift. Cons: materially more complex (local caching, conflict/replay logic, offline bill-numbering strategy). | **Option A for v1, Option B as an explicit fast-follow** — ship with hard local-server dependency but document this as a known operational risk (see Risk Register addendum, R-04) and prioritize Option B if the client's real-world server uptime data (once available) shows this is a frequent pain point. Rationale: Option B's complexity (especially safe offline bill-numbering) is substantial; better to ship the simpler model, monitor real failure rates, and invest in resilience only if evidence justifies it, rather than over-engineer speculatively. | Engineering Lead | Open |
| **DEC-021** | Global order-identifier scheme built on per-outlet-local bill/KOT sequences | System Configuration confirms "Reset Bill No." as a local admin action, establishing bill/KOT numbering is per-outlet-local and resettable — meaning raw bill numbers are not globally unique or monotonic, which is a problem for cloud-side cross-outlet reporting and any external references (payment gateway receipts, aggregator order IDs shown to customers). | (A) Cloud-side global order ID = `outlet_code + local_bill_seq + reset_epoch` (a monotonic "reset epoch" counter incremented every time local bill numbers are reset, to disambiguate reused numbers after a reset). Pros: preserves the human-readable local bill number staff and customers already see, while making the cloud key genuinely unique even across resets. Cons: requires the reset action itself to be a synced, audited event (which DEC-010/local-audit design must support). (B) Cloud generates its own independent UUID/ULID per order at sync time, unrelated to the local bill number, which becomes purely a display field. Pros: trivially globally unique, no dependency on reset-event syncing being reliable. Cons: two numbering systems for humans to reconcile (the receipt number a customer has vs. the internal ID support/ops use), more confusing during dispute resolution. | **Option A** — `outlet_code + local_bill_seq + reset_epoch` as the cloud-global key, with reset events themselves treated as first-class synced/audited records. Rationale: keeps the customer-facing bill number meaningful (ties directly to what's printed on the receipt) while solving uniqueness, and reuses the audit infrastructure that recording "Reset Bill No." events already requires under DEC-010. | Engineering Lead | Open |
| **DEC-022** | Manual Grand-Total edit on settled orders: approval level, audit, and v1 allowance | Order History shows a pencil/edit icon against historical orders that appears to allow editing the Grand Total after the fact, including (per the icon's placement) potentially post-payment. No screenshot shows a confirmation/approval dialog or audit trail for this action. | (A) Disallow entirely in v1 — Grand Total becomes immutable once an order reaches Paid status; any correction must go through a formal void-and-rebill flow instead. Pros: eliminates a major reconciliation-integrity risk category entirely; simpler v1 scope. Cons: diverges from observed reference-app capability, may frustrate staff used to quick corrections, and doesn't match "we're cloning KapMeta" expectations if the client specifically wants parity. (B) Allow it, but gate behind a manager-level PIN/role check, require a mandatory reason code + free-text note, write an immutable audit-log row (old value, new value, editor, timestamp, reason), and flag such orders distinctly in Day-End and Item reports so a reconciler can always see they were adjusted. Pros: matches reference-app behavior and real-world need for quick fixes (e.g. a miskeyed total), while containing the risk with audit trail and reporting visibility. Cons: more schema/UI work (audit table, role/permission check, reporting flags). | **Option B** — allow manager-gated, audited, reason-coded edits to Grand Total on settled orders, with mandatory surfacing in Day-End/reconciliation reports. Rationale: this matches confirmed reference-app capability and real restaurant operational needs (staff need a fast correction path), and the audit/role controls are a standard, well-understood mitigation rather than a novel risk — full disallowance (Option A) would be safer but is a significant behavior regression versus the system being cloned. | Compliance + Engineering Lead (joint) | Open |
| **DEC-023** | Multi-outlet support: in scope for v1? | All 86 screenshots were captured against exactly one outlet ("Hotel kapila"); no multi-outlet switcher, outlet-selector, or cross-outlet aggregation screen was observed anywhere in the App Shell or System Configuration. | (A) Single-outlet-only for v1: schema, auth, and sync are all designed with an implicit single-tenant-outlet assumption (simpler now), with multi-outlet explicitly deferred to a later phase requiring a dedicated migration project. Pros: fastest path to v1 given the actual evidence available; avoids speculative complexity. Cons: real risk of a painful, costly migration later if the client does in fact need multi-outlet sooner than expected — every table implicitly needs an `outlet_id` retrofitted, and access-control/reporting rework follows. (B) Design the schema multi-outlet-ready from day one (every table gets `outlet_id` as a first-class key even if v1 UI only ever shows one), while still shipping single-outlet UI/UX for v1. Pros: avoids the costly retrofit risk in (A) at comparatively low incremental cost if done at schema-design time; cheap insurance. Cons: some added complexity now (every query needs outlet scoping) for a benefit that may never be needed if the client truly stays single-outlet. | **Option B** — treat multi-outlet as out of scope for v1 **UI/UX**, but require `outlet_id` as a first-class scoping key across the schema from the start. Rationale: the cost of designing outlet-scoped tables up front is low relative to the cost of retrofitting outlet scoping across an already-live single-tenant schema later (documented as Risk R-01 below); this is a case where modest present-day discipline meaningfully de-risks the future, independent of whatever the final v1-scope decision turns out to be. | Product + Engineering Lead (joint) | Open |
| **DEC-024** | OOS (item availability) vs channel On/Off (deliberate listing): one flag or two? | Mark-OOS Modal and Menu Online-Availability Manager screenshots show what appear to be two distinct, independently-operated mechanisms: an "Out of Stock" toggle (presumably ingredient/inventory-driven, possibly time-bound) and a separate per-channel online-availability On/Off toggle (presumably a deliberate merchandising/listing decision, e.g. hiding an item from Zomato without marking it physically out of stock). | (A) Collapse into a single `is_available` boolean per item (optionally per channel) — simpler schema, "unavailable" is "unavailable" regardless of cause. Pros: minimal schema. Cons: loses the distinct causes ("we ran out" vs "we chose not to sell this online right now"), which matters operationally (OOS should probably auto-expire/reset, deliberate off-channel listing should not) and for reporting (a restaurant manager needs to distinguish inventory failures from merchandising choices). (B) Model as two independent, separately-audited boolean/state fields per item-channel: `is_oos` (inventory-driven, likely time-bound/auto-reset, single audit trail of stockouts) and `channel_listed` (merchandising-driven, per-channel, persists until deliberately changed) — with effective availability computed as `channel_listed AND NOT is_oos`. Pros: matches the two distinct UI mechanisms directly observed, supports meaningfully different reporting (stockout frequency vs. deliberate delisting), and avoids conflating an operational failure with a business decision. Cons: more schema/UI surface, and the two states must be composed correctly everywhere availability is checked (menu display, order acceptance, aggregator sync). | **Option B** — two distinct, independently-audited fields (`is_oos`, `channel_listed`) composed into effective availability. Rationale: the reference app's own UI already separates these into two different screens/modals, strongly suggesting the product team considers them operationally distinct; collapsing them in this clone would lose real reporting value (e.g. "how often do we run out of X" vs. "which items are we deliberately not selling on Zomato") for minimal schema savings. | Product | Open |

## Definition of Ready — Addendum (for `docs/00-governance/definition-of-ready-done.md`)

The following POS-domain-specific checklist items should be added to the Definition of Ready before any epic touching the affected areas moves into development:

- [ ] Tax mode (Backward vs Forward) per sales channel confirmed directly with the client, resolving the apparent contradiction in DEC-017, before any invoice/billing schema work starts.
- [ ] Canonical `order_status` and `table_session_state` enums (DEC-016) are documented, reviewed by Engineering Lead, and referenced in the API contract before Order Entry or Order History epics start.
- [ ] Multi-outlet in/out-of-scope decision (DEC-023) is signed off, and if "out of scope for v1 UI but schema-ready," the `outlet_id` scoping convention is documented in the schema style guide before the first migration is written.
- [ ] Money-field glossary (DEC-015: `line_total` / `order_grand_total` / `settlement_amount`) is published and linked from any story touching billing, payments, or Day-End reporting.
- [ ] Grand-Total edit policy (DEC-022) — role/permission model, audit table shape, and reporting-flag requirement — is agreed before the Order History edit feature is built.
- [ ] Sync SLA / offline-tolerance thresholds (DEC-019) and local-server-down terminal behavior (DEC-020) are documented and referenced in any story implementing sync, connectivity banners, or offline queuing.
- [ ] Global order-identifier scheme (DEC-021) is agreed before the cloud-side order table's primary/unique keys are finalized.
- [ ] OOS vs channel-listing data model (DEC-024) is agreed before the Menu Availability or Aggregator Sync epics start.
- [ ] Any story that would otherwise need "demo" business data (menu items, prices, tax rates, outlets, payment-type labels) has an identified DB table + seed/migration path or admin-UI write path per the project's no-hardcode-data rule — confirmed in the story description, not just assumed.
- [ ] For any item still marked "Open" and blocking in this addendum (notably DEC-013 MFR button and DEC-014 Sales Return fields), either ground-truth evidence has been obtained, or the story is explicitly scoped to exclude the ambiguous behavior with a follow-up ticket filed.

## Risk Register — Addendum (for `docs/00-governance/risk-register.md`)

| Risk ID | Description | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| **R-01** | Schema is built implicitly single-outlet (no `outlet_id` scoping) and the client later needs multi-outlet, forcing a costly retrofit migration across every table plus access-control and reporting rework. | Medium | High | Adopt DEC-023 Option B now: require `outlet_id` as a first-class key on every tenant-scoped table from the first migration, even while v1 UI supports only one outlet. Low-cost insurance relative to retrofit cost. |
| **R-02** | The OOS/channel-availability fan-out to multiple aggregator platforms (Swiggy, Zomato, etc.) partially fails — e.g. Zomato's API call succeeds but Swiggy's silently fails — leaving a stale "available" listing on one platform for an item that's actually out of stock, causing order acceptance for an item the kitchen can't fulfill. | Medium | High | Design the fan-out as a per-platform job queue with explicit per-platform success/failure status surfaced in the Menu Availability Manager UI (not a single aggregate "done" state), plus automatic retry with backoff and an alert/badge on any item with a platform in a failed-sync state for more than a defined threshold. |
| **R-03** | Manual Grand-Total edits on settled/paid orders (DEC-022) create day-end reconciliation gaps between cash/card settlement totals and reported order totals, especially if edits happen after the payment-type summary has already been generated for that business day. | Medium | Medium | Require Day-End Summary generation to explicitly flag and separately total any orders edited after their original Paid timestamp; block Grand-Total edits on orders belonging to an already-closed/locked business day without a distinct "reopen day" admin action that is itself audited. |
| **R-04** | Local terminals hard-depend on the local outlet-server (per DEC-020 v1 decision); a local-server outage during peak service halts all order entry and billing at that outlet with no fallback, causing direct revenue/operational impact and reputational risk. | Medium | High | Document this as an explicit known limitation in client-facing v1 scope communication; instrument local-server uptime from day one so real failure-rate data (not guesswork) drives the DEC-020 fast-follow investment decision; provide an ops runbook for a "manual paper ticket" fallback procedure while the design is single-server-dependent. |
| **R-05** | The Backward-Tax/Forward-Tax ambiguity (DEC-017) is resolved incorrectly (e.g. built as a strict outlet-global toggle when the client actually needs simultaneous per-channel modes, or vice versa), producing incorrect tax on printed invoices — a compliance/legal exposure, not just a UX bug. | Low-Medium | High | Do not close DEC-017 on internal analysis alone; require an explicit client/compliance confirmation call specifically on this point before the Tax Master schema is frozen, and add a targeted test case comparing generated invoice tax lines against the reference app's captured dine-in and online tax rows for the same nominal rate. |
