# 0004. Per-Outlet Local Sequence for Bill and KOT Numbers

## Status
Accepted

## Context
Printed bills and kitchen order tickets (KOTs) need short, sequential, human-readable numbers — staff read them aloud, write them on tickets, and reference them in disputes ("bill 8006 is missing an item"). Reference-app screenshots confirm this directly: real captured bills show small sequential numbers such as Bill No. 8005, 8006, and so on, not UUIDs or globally scattered numbers.

The reference app's System Config also exposes a "Reset Bill No." admin action. That capability only makes sense if the numbering sequence is something a single outlet's local admin can reset without affecting or coordinating with any other outlet — i.e., the sequence is local to the outlet, not a shared global counter. A globally unique, cloud-coordinated sequence could not be reset by one outlet's local admin without either affecting other outlets or requiring a round trip to a central authority (which would also violate the offline-first requirement of ADR-0002).

At the same time, every order needs a globally unique identifier for cross-system references — sync (ADR-0003), aggregator order correlation, cross-outlet reporting (ADR-0005) — that cannot collide across outlets and does not depend on any central coordinator to generate.

## Decision
Two distinct identifiers are used for orders/bills/KOTs:

- **`order_id`**: a globally unique identifier (UUID), generated locally by the outlet-server (or, for aggregator-originated orders, by the cloud backend) at creation time with no coordination required. This is the identifier used for all cross-system references: sync outbox/inbox entries, aggregator order correlation, cross-outlet reporting joins, API responses, and any inter-service reference.
- **`bill_no`** and **`kot_no`**: outlet-local integer sequences, generated by each outlet-server independently for its own outlet only. These are not unique across outlets and are never used as a cross-system reference key — they exist solely for staff-facing and printed-document display (bills, kitchen tickets, verbal reference during service).

The outlet-local admin "Reset Bill No." (and equivalent "Reset KOT No.") action resets that outlet's local sequence only, with no coordination with the cloud or other outlets required, matching the observed reference-app capability. Every table and record that stores `bill_no`/`kot_no` also stores `outlet_id` (per ADR-0005) and `order_id`, so a `bill_no` is only ever meaningful in the context of `(outlet_id, bill_no)`, never on its own.

## Consequences

**Positive**
- Directly matches confirmed real-world product behavior: sequential, resettable, short bill/KOT numbers per outlet, and a "Reset Bill No." action that requires no cross-outlet coordination to implement or to reason about.
- Bill/KOT sequence generation is a purely local operation with no dependency on cloud connectivity or a central sequence authority — consistent with the offline-first requirement in ADR-0002.
- `order_id` gives every system component (sync, reporting, aggregator correlation) a single unambiguous global key, so `bill_no` collisions across outlets are a non-issue by design — nothing outside the printed-document/display context ever keys off `bill_no` alone.
- Resetting a sequence at one outlet has zero blast radius on any other outlet or on the cloud's records, since the cloud always references orders by `order_id`.

**Negative**
- Every piece of code, query, or report that displays or filters by `bill_no`/`kot_no` must also scope by `outlet_id`, or it will silently produce wrong results once more than one outlet exists (e.g., "find bill 8006" must always be "find bill 8006 at outlet X"). This needs to be enforced by convention/review and ideally by a composite key or constraint at the database level.
- Any future feature that wants a bill number to be meaningful across outlets (e.g., a single combined receipt spanning outlets, which is not a realistic scenario but illustrates the limit) is not supported by this design — that was intentionally out of scope.
- Sequence gaps can still occur (e.g., a voided order in some flows), which is normal for this class of scheme but should be communicated to support/finance so it isn't mistaken for missing data during audits.

## Alternatives Considered

**Single global auto-increment sequence across all outlets.** Rejected: breaks the "Reset Bill No." semantics observed in the reference app — resetting a global counter would affect every outlet simultaneously, or would require the reset to somehow apply only going forward for one outlet while others keep incrementing, which is not what a simple reset action implies. It would also produce bill numbers that jump unpredictably at any given outlet as other outlets create orders concurrently, which does not match the clean sequential numbering seen on real printed bills.

**UUID-only, with no human-friendly sequential number at all.** Rejected: does not match the real captured reference-app UI, which clearly displays short sequential numbers (Bill No. 8005, 8006, ...) to staff and on printed output. A UUID is unusable for a cashier reading a number aloud or a kitchen ticket staff need to call out quickly, so this alternative fails the actual operational use case even though it would simplify the identifier scheme.
